笔记一：ReAct 循环 — Agent 如何"思考再行动"

1.1 什么是 ReAct

ReAct = Reasoning + Acting。Agent 不是"看到问题直接回答"，而是经历一个循环：

Thought（思考）→ Action（行动/调用工具）→ Observation（观察工具结果）→ Thought（再思考）→ ... → Final Answer（最终回答）

Martin 项目把这个循环交给 LangGraph 的 create_agent 自动编排，开发者只需定义工具，LangGraph 负责循环控制。

1.2 为什么需要 Thought 环节

核心认知 Observation → Thought 这一步是 Agent 决策质量的瓶颈。没有它，Agent 就是闭着眼睛做多步决策。

实例：Agent 调了 analyze_image，返回"检测到 3 个结节，最大 5.2mm"。

没有 Thought有 Thought
LLM 随机选下一个工具，可能又问一遍"请上传 CT" LLM 推理："5.2mm 属于小结节，需要查 Fleischner 指南判断风险等级 → 下一步调 search_medical_knowledge"

Thought 的本质是：让 LLM 基于"刚才看到了什么"来决定"接下来做什么"。这是多步推理的根基。

1.3 Martin 项目中的体现

在 prompt.py 中，每个工具的参数 schema 都强制包含一个 reasoning 字段：

analyze_image 工具的参数:
  image_path: string, 必填
  reasoning: string, 必填  ← 强制要求：调用这个工具前，先说明为什么

这不是为了审计日志，而是为了确保 LLM 在调用工具前真正"想了一下"。

1.4 常见误解：每次循环只能用一个工具？

误解：每次循环只能用一个工具 Function Calling 支持并行调用。LLM 可以在同一轮返回多个 tool_calls，LangGraph 收到后并行执行。

实锤：Martin 审计日志中的并行调用

来自 audit/677326aa_20260714_192051.jsonl 的真实运行记录：

第 1 轮（串行）——只能先检测，因为不知道 CT 里有什么：

19:36:50.161  analyze_image  ← 只返回了 1 个 tool_call
  reasoning: "用户提供了CT路径…优先调用analyze_image进行结节检测"

第 2 轮（并行！）——检测结果已拿到，两个后续操作互不依赖：

19:39:42.894478  update_case_context    ← 同一微秒！
  reasoning: "用户提供了患者信息…需要更新到病例上下文"
19:39:42.894478  retrieve_knowledge     ← 同一微秒！
  reasoning: "需要根据检测结果检索知识库…获取Lung-RADS随访建议"

第 3 轮（五个工具并行！）——全部基于前两轮的结果，互相独立：

19:41:33.317545  analyze_image          ← 重新检测
19:41:33.317545  update_case_context    ← 更新患者信息
19:41:33.317545  retrieve_knowledge     ← 检索指南
19:41:33.317545  update_case_context    ← 补充吸烟史细节
19:41:33.317545  generate_report        ← 生成详细报告
  ↑ 五个工具全部在同一微秒，LLM 一次性返回了 5 个 tool_calls
关键规律：LLM 自己判断依赖关系
  • 第 1 轮：只有 analyze_image——必须先知道结果才能决定下一步
  • 第 2 轮：update_case_context + retrieve_knowledge 并行——互不依赖
  • 第 3 轮：5 个工具全部并行——全部基于前两轮的结果，互相独立
不需要代码告诉 LLM"先 A 再 B"。LLM 看到依赖就串行，看到独立就并行。

1.5 关键结论

  • ReAct 循环不是"多此一举"，而是 Agent 具备多步推理能力的基础
  • Thought 环节让每个工具调用都是"有目的的"，不是随机的
  • Function Calling 支持并行，不必担心循环开销过大

笔记二：双记忆系统 — 为什么 Agent 需要两套"记忆"

2.1 两种记忆，两种职责

记忆类型Martin 实现存什么特点
对话记忆
(Episodic Memory)		 LangGraph SqliteSaver 完整对话历史：
用户说了什么、Agent 回答了什么		 非结构化、按时间顺序、
支持"刚才聊了什么"
事实记忆
(Working Memory)		 CaseContext 结构化关键事实：
年龄、性别、结节列表、风险因素		 结构化、精确、不丢失、
支持"患者基本信息是什么"

这个设计借鉴了认知科学中"情景记忆"（记得发生过什么）和"工作记忆"（当前正在处理的关键信息）的区分。

2.2 如果只有一套会怎样

只有对话历史，没有 CaseContext

用户第 1 轮："患者 56 岁，男性，吸烟 30 年"
用户第 10 轮："这个结节风险大吗？"

Agent："根据您的年龄和吸烟史...呃，您今年多大来着？"
——对话太长，上下文窗口前面被截断，年龄丢了。

只有 CaseContext，没有对话历史

用户第 1 轮："分析这个 CT" → Agent 检测到 3 个结节
用户第 2 轮："第 2 个结节怎么看？"

Agent："请问您说的是哪个结节？"
——CaseContext 存了结果，但没有对话连续性，Agent 不知道"第 2 个"指的是什么。

2.3 为什么"从对话历史里提取信息"不可靠

很多人会想："对话历史里不是有年龄信息吗？让 LLM 自己读不就行了？"

问题在于：

  1. 上下文窗口有限：对话长了，前面的信息会被截断
  2. LLM 注意力衰减：上下文越长，LLM 越容易忽略中间的关键信息
  3. 提取不可靠：LLM 可能把"56 岁"记成"65 岁"

所以 CaseContext 单独维护一份结构化数据，不依赖 LLM 的"记忆力"。每次对话时，把 CaseContext 作为已知信息注入，让 LLM 直接使用，而不是靠回忆。

2.4 Martin 项目中的实现

核心设计：CaseContext 借 Checkpointer 的消息通道实现读写

一句话精髓 LangGraph Checkpointer 是一套统一的存储抽象层，有三种实现。CaseContext 不关心底层是哪种——它只通过 Checkpointer 的统一接口读写，把自己的 JSON 塞进消息通道里就获得了持久化。

Checkpointer 的三种实现

实现存储在哪进程重启后？多实例共享？Martin 用在哪
MemorySaver 内存 dict 全丢 不能 单元测试（跑完即弃）
SQLiteSaver 单机文件 sessions.sqlite 持久 不能（文件锁） 生产环境
PostgreSQLSaver 网络数据库服务器 持久 可以（多实例共享） 未来扩展方向

Martin 代码中的体现（sessions.py）：

def create_memory_checkpointer():           ← 测试用，跑完就丢
    return CheckpointerManager(MemorySaver())

def get_default_checkpointer(db_path=None):  ← 生产用，持久化
    context = SqliteSaver.from_conn_string(db_path)
    # db_path = "data/sessions.sqlite"

为什么换存储不影响 CaseContext 一行代码

CaseContext 不直接读写 SQLite。它通过 Checkpointer 的统一消息通道工作：

① 注入时（写）：把 CaseContext 序列化成 JSON，拼在用户消息前面。LangGraph 自动把这条消息存入 Checkpointer——不管底层是 SQLite 还是 PostgreSQL。

messages = [
    HumanMessage("【当前病例上下文 JSON】{年龄:56, 性别:男, ...}  ← 自动存入 Checkpointer
                  【当前病例上下文】年龄:56岁 性别:男..."),
    HumanMessage("这个结节风险大吗？"),
]
self._agent.invoke({"messages": messages}, config={"thread_id": "abc-123"})

② 读取时（从 Checkpointer 恢复）：在历史消息里找那条带 CONTEXT_MESSAGE_PREFIX 的消息，直接 json.loads() 反序列化。

for message in reversed(checkpoint_messages):
    if content.startswith("【当前病例上下文 JSON】"):
        payload = content[前缀长度:]
        return json.loads(payload)     ← 零信息损失

③ 显示时（过滤掉）：用户查看历史记录时，注入消息被 _is_context_message() 过滤——前端只看到正常对话。

精确表述（纠正之前的说法） 之前说的"Checkpointer 是数据库"不够精确。正确的是：Checkpointer 是 LangGraph 的统一存储抽象层，它有三个实现。CaseContext 不依赖任何具体实现，只通过 Checkpointer 的统一接口读写消息。这就是"借力"——底层存储由 LangGraph 统一管理，CaseContext 只负责数据结构化。换成 PostgreSQL，CaseContext 一行代码都不用改。

Domain-Specific Context Injection 模式

这个设计有自己的名字——Domain-Specific Context Injection（领域特定上下文注入）。它的核心思想：

  1. LangGraph Checkpointer 管理通用的对话状态（消息序列、工具调用记录）——它不懂"患者信息"、"结节列表"这些医学概念
  2. CaseContext 管理领域特定的结构化状态（年龄、性别、结节坐标）——它不懂"对话"、"消息"这些聊天概念
  3. 每次 invoke() 前，CaseContext 序列化后注入到消息流中；invoke() 后，从工具结果中同步更新

两者通过 thread_id 关联，各自按自己的方式存储，互不干扰但保持同步。

隔离机制：同一个 key，两个存储系统

thread_id = "abc-123"                     thread_id = "def-456"
─────────────────────                     ─────────────────────

_context_cache (进程内存)                   _context_cache (进程内存)
  "abc-123" → CaseContext                    "def-456" → CaseContext
  {年龄:62, 结节:[...]}                      {年龄:45, 结节:[...]}
         │                                          │
         │ 备份（JSON 消息形式）                       │ 备份
         ▼                                          ▼
Checkpointer (SQLite 文件)                   Checkpointer (SQLite 文件)
  WHERE thread_id="abc-123"                   WHERE thread_id="def-456"
  ├─ checkpoint_1: 对话消息                     ├─ checkpoint_1: 对话消息
  ├─ checkpoint_2: 对话消息                     ├─ checkpoint_2: 对话消息
  └─ checkpoint_n: 【JSON】{年龄:62...}         └─ checkpoint_n: 【JSON】{年龄:45...}

CaseContext 的三种创建/恢复场景

每次 AgentExecutor.__init__() 都要解决同一个问题：这个 thread_id 的 CaseContext 在哪？

为什么 AgentExecutor 和 LLM client 是请求级，而不是进程级？
因为它们没有需要跨请求共享的状态。对话历史在 Checkpointer 里，病例信息在 _context_cache 里。AgentExecutor 只是一个"执行器壳"——创建成本极低（就是 new 几个对象），用完即弃反而避免了内存泄漏和并发安全问题。

2.5 关键结论

  • 对话历史解决"上下文连续性"（知道刚才在聊什么）
  • CaseContext 解决"事实准确性"（记住关键信息，精确不丢失）
  • 两者互补，缺一不可

笔记三：工具设计 — 什么时候写新工具，什么时候让 Agent 自己组合

3.0 前置概念：Martin 当前是 Workflow 还是 Agent？

一句话答案 Martin 是 单 Agent + 软 Workflow。没有硬编码的执行路径，所有决策权在 LLM 手里。Prompt 里的 Workflow 指引只是给 LLM 看的"说明书"，不是代码里的 if-else。

三个概念的层级关系

概念层级解决的问题Martin 现状
Multi-Agent 系统架构 多个专家怎么协作？ 未使用 单 Agent 目前够用
Workflow Agent 内部 任务按什么顺序执行？ 软 Workflow Prompt 指引，LLM 动态决策
Tool 原子能力 具体做什么？ 6 个工具（analyze_image 等）

它们不是"二选一"，而是不同层级的东西：多 Agent 系统里每个 Agent 内部可能用 Workflow 组织行为，每个 Workflow 节点可能调用 LLM 或 Tool。

Martin 的实际情况：全交给 LLM 动态决策

invoke() 方法的核心逻辑极其简单（agent.py）：

result = self._agent.invoke(
    {"messages": messages},
    config=config,
)
# 没有任何 if-else 判断场景！全交给 LLM

Prompt 里的 Workflow 部分只是纯文本指引，不是代码：

# 这是 Prompt 里的文字，不是代码逻辑！
- 如果医生上传 CT 文件 → 直接调用 analyze_image
- 如果医生提供患者信息 → 调用 update_case_context
- 如果检测完成，医生需要解释 → 调用 retrieve_knowledge

LLM 读完这段文字后，自己判断当前输入属于哪种情况，然后决定调哪个工具。路径不确定——同样输入可能走不同的工具链。

什么时候应该从"软 Workflow"升级到"硬 Workflow"？

对照 Anthropic 的标准：

"When a task can be clearly defined with fixed steps, use Workflow. Only use Agent when the path can't be predicted." 当你发现 LLM 在某个场景下经常走错路径，就是该硬编码的时候了。

举个例子，假设医生上传 CT 后 LLM 有时候不调 analyze_image 反而先闲聊：

# 未来可能的硬编码——但 Martin 目前不需要
def invoke(self, inputs):
    user_input = inputs.get("input", "")
    
    # 检测到文件路径 → 必定先执行 analyze_image
    if self._contains_image_path(user_input):
        detection = analyze_image.invoke(...)
        inputs["input"] = f"检测结果：{detection}\n\n用户问题：{user_input}"
    
    return self._agent.invoke(...)

但目前不需要。 DeepSeek 对 Martin 的 System Prompt 理解足够好，没有报告走错路径的问题。

与笔记四的联系：软约束 vs 硬约束 的同构关系

软 Workflow 和 软约束实际上是同一套设计哲学的两种表现：

软（Prompt 层）硬（Code 层）
约束层面
（笔记四）		 Prompt 里写"输出 Markdown 格式"
LLM 可能遵守，也可能不遵守		 代码里 json.loads() 校验格式
不合法就报错
流程层面
（本笔记）		 Prompt 里写"如果上传 CT → 调 analyze_image"
LLM 可能先分析，也可能先闲聊		 代码里 if has_image_path: 先执行 analyze_image
必定走这条路径

判断标准完全一致：如果"出错"不可接受，用硬的。格式错误不可接受 → 硬约束。流程走错不可接受 → 硬 Workflow。目前 Martin 两个层面都在用软的——因为 DeepSeek 表现得足够好，还没到必须上硬的临界点。

什么时候需要多 Agent？

多 Agent 的标志：不同角色需要不同的 System Prompt、不同的工具集、不同的知识边界。

状态判断做法
一个 Prompt 能写清楚所有规则 单 Agent 不同场景 = 不同 Workflow 路径
Prompt 太长，不同规则开始冲突 考虑拆分 不同角色 = 不同 Agent
不同子任务需要不同工具集 需要多 Agent Orchestrator-Workers 模式

Martin 未来可能的多 Agent 场景：

医生："这个结节是恶性的吗？需要手术吗？"
  ↓
Orchestrator Agent（调度员）
  ├──→ 影像分析 Agent   工具：[analyze_image, compare_nodules]
  │     System Prompt："你是影像学专家，专注CT特征分析..."
  │     输出：结节的位置、大小、密度、边缘特征
  │
  ├──→ 临床决策 Agent   工具：[retrieve_knowledge, search_guidelines]
  │     System Prompt："你是临床决策支持专家，基于指南评估..."
  │     输出：Lung-RADS 分级、恶性概率、随访建议
  │
  └──→ 调度员汇总 → 综合报告

为什么这里需要多 Agent？影像专家和临床决策专家的"人设"完全不同，塞进同一个 Prompt 会互相干扰；影像 Agent 不需要知识库，临床 Agent 不需要 MONAI；各自的上下文窗口互不污染。

Martin 的演进路线
  • 当前：单 Agent + 软 Workflow（一个 Prompt，LLM 动态选工具）
  • 近期：单 Agent + 更复杂的 Workflow（新增 compare_nodules 工具）
  • 中长期：多 Agent（影像分析 + 临床决策 + 报告生成各自独立）

3.1 判断标准

核心问题：Agent 自己能推理出多步操作吗？
  • 能 → 让 Agent 用现有工具组合
  • 不能 → 需要新工具

3.2 两个案例对比

场景Agent 能自己推理吗？决策
"帮我分析这个 CT" 能 输入有 CT → 我知道该调 analyze_image 现有工具，Agent 自己组合
"对比当前 CT 和 3 个月前 CT 的结节变化" 不能 需要：找到历史 CT 路径、坐标匹配、计算体积变化率——这些 LLM 不可能凭空推理 需要新工具 compare_nodules

3.3 为什么"对比结节"需要新工具

对比结节的难点在于精确计算：

  • 两个 CT 的结节坐标需要空间匹配（判断"结节 A 在两个 CT 里是同一个吗"）
  • 直径和体积变化需要数值计算（"从 5.2mm 增长到 5.8mm，增长率 11.5%"）
  • 这些是 LLM 的盲区——LLM 擅长"判断"但不擅长"精确计算"

所以应该做成 compare_nodules 工具，内部用 Python 做精确坐标匹配和尺寸对比，LLM 只负责调用工具并解释结果。

3.4 Agent 的边界在哪里

LLM 擅长
  • 理解自然语言意图
  • 判断"接下来该做什么"
  • 解释和总结
  • 灵活处理未预见的场景
LLM 不擅长
  • 精确数值计算
  • 确定性逻辑（if-else 分支）
  • 需要多个步骤精确配合的流程
  • 访问外部系统（数据库、API）

好的 Agent 设计 = LLM 做决策 + 代码做执行。工具是连接两者的桥梁。

3.5 Martin 项目的 6 个工具分类

类别工具LLM 做什么代码做什么

3.6 关键结论

  • 判断标准：Agent 自己能推理出多步操作吗？
  • LLM 擅长判断，不擅长精确计算
  • 工具是 LLM 和代码的分界线

3.7 对照 Anthropic "Building Effective Agents" 深入解读

3.7.1 Anthropic 的核心原则

"Success isn't about building the most sophisticated system — it's about building the right system for your needs. Start with simple solutions, only add complexity when it demonstrably improves outcomes." 不是比谁架构更复杂，而是比谁更合适。从最简单的方案开始，只在被证明有效时才加复杂度。

这就是 Q3 的决策框架本身——"要不要做新工具"不是拍脑袋决定，而是先问：现有方案真的不够用吗？

3.7.2 对照五种 Workflow 模式：Q3 的场景分析

Anthropic 描述了 5 种 Workflow 模式。Q3（"对比两次 CT 的结节变化"）适合哪种？

不适合：Prompt Chaining（提示链）

analyze_image(CT-1) → LLM解读 → analyze_image(CT-2) → LLM解读 → LLM自己对比
问题：LLM 在最后一步无法做精确的结节匹配和数值对比，会幻觉

适合：Orchestrator-Workers + 专用工具

               ┌── analyze_image(CT-1) → 结节列表1
Orchestrator ──┤
  (LLM)        └── analyze_image(CT-2) → 结节列表2
                      ↓
               compare_nodules(列表1, 列表2)  ← 新工具（确定性算法）
                      ↓
               LLM 解读对比结果 → 报告

这里 compare_nodules 就是那个应该做成新工具的东西。它不是让 LLM 去算，而是内部用确定性算法：

  • 坐标匹配：基于解剖标志的刚性配准 + 匈牙利算法做结节配对
  • 精确计算：体积变化率、直径变化量——这些 LLM 的数学能力不可靠
  • 结构化输出：返回配对结果和变化数据，供 LLM 解读（不是自然语言）

3.7.3 工具设计三原则（Appendix 2）+ compare_nodules 对照

Anthropic 附录给出了工具设计的三个原则，直接指导 compare_nodules 的设计：

原则含义compare_nodules 怎么做
1. Give tokens to think 工具描述像给初级开发者写的 docstring：用途、何时用、输入输出格式、边界条件、与其它工具的区别 明确写"何时调用：医生要求对比两次检查时"；列出 matched_pairs / unmatched / registration_quality 字段；区分与 analyze_image 的职责
2. Keep format natural 输入输出格式自然衔接，不给 LLM 增加格式转换负担 输入直接接受 analyze_image 的原生输出，LLM 不需要重新格式化；输出结构化数据直接可用于报告
3. No formatting overhead 避免让 LLM 做无聊的格式工作 LLM 只负责解读临床意义和生成自然语言报告，坐标对齐和数值计算完全由工具内部处理

具体工具描述示例（Anthropic 风格）：

"""compare_nodules: 对比两次 CT 扫描的肺结节变化。

何时调用：医生明确要求对比两次检查结果时（如"和上次比怎么样了"）。

输入：两次 analyze_image 的返回结果（结节列表，含位置/直径/体积）。
输出：每个结节的配对结果和变化量：
  - matched_pairs: [{nodule_1_id, nodule_2_id, volume_change_pct, 
                      diameter_change_mm, status}]
  - unmatched_1: [仅在旧片出现的结节]
  - unmatched_2: [仅在新片出现的结节]
  - registration_quality: 配准质量评分 (0-1)

与 analyze_image 的区别：analyze_image 是单次检测，compare_nodules 是纵向对比。
边界条件：如果配准质量 < 0.5，结果可能不可靠，需提醒医生。
"""

3.7.4 三步判断法（通用）

以后遇到"要不要做成新工具"的问题，用这个框架：

1. 这个任务的难点是什么？
   ├── 语义理解 / 自然语言生成 → LLM 能做 → 不需要新工具
   └── 精确计算 / 空间推理 / 确定性操作 → LLM 不能做 → 继续判断

2. 现有工具组合能否覆盖？
   ├── 能 → 不需要新工具（Anthropic: "start simple"）
   └── 不能 → 新工具

3. 新工具的复杂度是否可接受？
   ├── 需要新模型/新数据库/新算法 → 谨慎，可能过度设计
   └── 只是编排现有能力 + 确定性算法 → 合理
对 Q3 的最终结论 难点是空间配准 + 精确计算 → LLM 不能做 → 现有工具不能覆盖 → 需要新工具。但它只是编排现有的 analyze_image + 确定性匹配算法，复杂度可接受。应该做，放在 Roadmap 短期规划中。

笔记四：Prompt 的边界 — 软约束与硬约束

4.1 核心认知：Prompt 不是"命令"，而是"建议"

关键理解 Prompt 里的规则是 软约束，不是硬约束。LLM 可以无视它们。你越是在 Prompt 里堆规则，越可能被忽略（上下文太长，LLM 注意力分散）。

你写"请用结构化 Markdown 输出"，LLM 可能输出 Markdown，也可能不输出。你写"绝对不能泄露患者姓名"，LLM 可能泄露，也可能不泄露。它只是"尽量"遵守，没有"强制"机制。

4.2 Prompt 能解决什么 vs 不能解决什么

Prompt 能解决Prompt 不能解决
风格引导："不要用模板化表达"精确计算："结节体积增长 23.7%"
角色定位："你是医学影像 Copilot"格式强制："必须输出合法 JSON"
简单约束："最多问 3 个问题"安全约束："绝对不能泄露患者姓名"
思维引导："先分析再回答"数据一致性："结节数必须和检测结果一致"

4.3 软约束 vs 硬约束的对比

软约束（Prompt）硬约束（Code）
如何实现在 System Prompt 里写规则在代码里写校验逻辑
可靠性不确定，LLM 可能忽略100% 确定
适用场景风格、角色、行为引导格式校验、数据提取、安全控制
Martin 示例"报告必须结构化"（prompt.py）用正则提取结节直径（routers/image.py）

4.4 Martin 项目中的"硬约束"实例

在 api/routers/image.py 中，analyze_image 工具返回的文本是自由格式的，但 API 路由用正则表达式强行提取结构化数据：

原始文本: "检测到结节总数: 3\n结节 1: 最大直径: 5.2mm\n  检测置信度: 0.95"

正则提取（代码层硬约束）:
  total_match = r"检测到结节总数:\s*(\d+)"     → 3
  diameter    = r"最大直径:\s*([\d.]+)"        → 5.2
  score       = r"检测置信度:\s*([\d.]+)"       → 0.95

这就是典型的"硬约束"：不管 LLM 输出的文本格式多乱，正则都能准确提取数字。如果让 LLM 自己输出 JSON，可能格式错误、字段缺失——但正则不会。

4.5 工程实践：什么时候用代码层约束

一个简单判断：如果"出错"是不可接受的，就用代码层约束。

  • 患者年龄不能为负数 → 代码校验
  • 报告格式不能错乱 → 用模板 + 代码填充，不让 LLM 自由发挥
  • 结节数量必须和检测结果一致 → 代码计数，LLM 只负责解释
  • 对话语气可以友好一点 → Prompt 引导

4.6 关键结论

  • Prompt 是软约束，Code 是硬约束
  • Agent 系统需要两者配合：Prompt 引导行为，Code 确保可靠性
  • 判断标准：如果出错不可接受，用代码层硬约束

设计决策：为什么把规则变成示例
给 LLM 写 10 条规则，不如给它看 1 个例子。例子让 LLM 直接模仿输出的结构和语气，比规则更高效。
这也是 OpenAI 官方指南的核心建议——Examples 不是锦上添花，是 Prompt 的必需组成部分。
变更风险提示

笔记五：分层架构 — 为什么核心引擎不能和 HTTP 层混在一起

5.1 什么是"端口与适配器"架构

也叫做 Hexagonal Architecture（六边形架构） 或 Clean Architecture。核心思想：

核心原则 业务逻辑（核心引擎）不应该依赖任何外部通信方式（HTTP、CLI、WebSocket、微信消息...）。反过来，外部通信方式可以依赖核心引擎。

5.2 Martin 项目的分层

CLI 终端
martin/__main__.py
input() + print()
FastAPI
api/routers/agent.py
HTTP + WebSocket
微信小程序
（未来）
wx.request()
↓↓ 全部调用同一个函数 ↓↓
martin/agent/agent.py
create_agent() → agent.invoke()
完全不感知谁在调用它

5.3 反面教材：如果混在一起会怎样

错误做法 — 把 Agent 逻辑写在 FastAPI 路由里

api/routers/agent.py
  def agent_chat():
    llm = ChatOpenAI(...)           ← Agent 逻辑
    tools = [analyze_image, ...]    ← Agent 逻辑
    agent = create_agent(...)        ← Agent 逻辑
    result = agent.invoke(...)       ← Agent 逻辑
    return result

如果要做微信小程序：
  → 需要新建 wechat/ 项目
  → 但 Agent 逻辑全在 api/ 里，没法复用
  → 要么复制粘贴一份（维护噩梦），要么重构（成本巨大）
正确做法 — Agent 逻辑独立，各层只做翻译

api/routers/agent.py
  def agent_chat():
    agent = create_agent(thread_id, checkpointer)  ← 调用核心引擎
    result = agent.invoke({"input": user_message})  ← 调用核心引擎
    return ChatResponse(output=result["output"])   ← 只做 HTTP 格式转换

wechat/handler.py（未来新建）
  def handle_message():
    agent = create_agent(thread_id, checkpointer)  ← 同样的调用
    result = agent.invoke({"input": user_message})  ← 同样的调用
    return TextMessage(content=result["output"])   ← 只做微信消息格式转换

5.4 为什么这很重要

混在一起分离后
接入新平台 = 复制 Agent 逻辑 = 两份代码维护 接入新平台 = 新建一个翻译层 = 核心代码 0 改动
改 Agent 逻辑要改 N 个文件 改 Agent 逻辑只改 martin/ 一个文件
测试 Agent 需要启动 HTTP 服务 测试 Agent 可以直接 `agent.invoke()`
HTTP 层的 bug 可能影响 Agent 逻辑 两层隔离，互不影响

5.5 验证：CLI 和 Web 调用的是同一个函数吗

对比两个入口，自己看：

CLI 版（martin/__main__.py）：

executor = build_agent(thread_id=session_id, checkpointer=checkpointer)
result = executor.invoke({"input": user_input})

Web 版（api/routers/agent.py）：

agent = create_agent(thread_id=session_id, checkpointer=checkpointer, verbose=False)
result = await asyncio.to_thread(agent.invoke, {"input": final_input})

唯一的区别：CLI 版用 build_agent()（多了日志回调），Web 版用 create_agent()（不需要日志）。核心调用 agent.invoke() 完全一样。

5.6 关键结论

  • 核心引擎不依赖任何外部通信方式
  • 每增加一种接入方式（微信、桌面 App、API...），只需新建一个翻译层
  • 核心代码 0 改动
  • 这就是"端口与适配器"架构的核心价值

笔记核心概念一句话
