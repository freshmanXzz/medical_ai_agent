## 一、Agent 架构学习

### 1.1 从单任务模型到 Agent 的认知升级

最初以为 AI 应用就是"调用 API"，做完这个项目才理解 Agent 的本质：

**单任务模式：**
```
输入 → 模型 → 输出
```

**Agent 模式：**
```
输入 → 推理 → 决定做什么 → 调用工具 → 观察结果 → 再推理 → ... → 输出
```

Agent 的核心不是模型有多强，而是**编排能力**——让模型学会"使用工具"和"规划任务"。

### 1.2 LangGraph 的 StateGraph 思维

以前写 Agent 是线性的"调模型 → 调工具 → 返回"。LangGraph 的 StateGraph 让我理解了：

- Agent 是一个**状态机**
- 每次推理都是状态的转移
- messages 是核心状态
- 工具调用是状态转移的动作

这种思维方式让 Agent 设计更清晰，也更容易扩展。

## 二、上下文管理的深度理解

### 2.1 核心洞见：结构化上下文 vs 对话历史

> **与其让 LLM 在每次对话中"从头阅读历史书"，不如给它一份"结构化摘要报告"。**

这是项目中最重要的学习收获。

#### 为什么对话历史不够？

一开始只依赖 LangGraph 的 MemorySaver，让 LLM 自己从对话历史中提取信息。但很快发现问题：

1. **Token 爆炸**：多轮对话后，每次调用都带着完整历史，成本高
2. **提取不可靠**：LLM 有时会遗漏关键信息，或者记错之前的内容
3. **业务数据混杂**：检测结果、患者信息都混在对话里，难以复用

#### CaseContext 的设计思路

把医学相关的**结构化数据**单独管理：

```python
class CaseContext:
    patient_info: dict      # 年龄、性别、吸烟史...
    image_info: dict        # 影像信息
    nodules: list           # 结节列表
    knowledge_summary: str  # 知识摘要
    clinical_notes: list    # 临床备注
```

每次对话前，把这些数据**格式化后注入**到 messages 最前面：

```
【当前病例上下文】
年龄：55 岁
性别：男
...

请基于以上病例信息理解后续问题。
```

#### 效果对比

| 维度 | 纯对话历史 | CaseContext + 对话历史 |
|------|-----------|----------------------|
| Token 消耗 | 线性增长（几千→几万） | 基本固定（几百） |
| 上下文准确性 | 依赖 LLM 记忆，不稳定 | 代码保证，100% 准确 |
| 可扩展性 | 差（加信息=加对话） | 好（加字段即可） |
| 业务复用 | 难（数据在文本里） | 易（结构化数据） |

### 2.2 这种优化方法的本质

在智能体领域，这叫做 **Structured State Management**（结构化状态管理），或者更具体地叫 **Domain-Specific Context Injection**（领域特定上下文注入）。

**核心思想：**
- LLM 负责**推理**，不负责**记忆**
- 代码负责**管理状态**，把相关信息"喂"给 LLM
- 对话历史负责"对话流"，结构化数据负责"业务流"

**适用场景：**
- 专业领域 Agent（医疗、法律、金融）
- 需要精确数据的场景
- Token 成本敏感的场景
- 多轮对话长流程

## 三、RAG 技术学习

### 3.1 RAG 不是"搜一下就行"

以前以为 RAG 就是把文档存到向量库，然后查询。实际做了才知道里面的学问：

1. **文档切分**：怎么切、切多大，直接影响检索质量
2. **查询构建**：不是直接搜，而是要"语义化"查询
3. **结果排序**：相似度阈值、去重、过滤
4. **注入方式**：怎么把检索结果放进 prompt 最有效
5. **引用标注**：[知识N] 机制，让输出可追溯

### 3.2 医学 RAG 的特殊挑战

- 术语专业，普通嵌入模型效果打折
- 需要精确匹配（比如 Lung-RADS 分级标准不能错）
- 多模态知识（文字 + 影像表现）

## 四、LangChain / LangGraph 学习

### 4.1 LCEL 的魅力

LCEL（LangChain Expression Language）用管道操作符 `|` 串联组件，声明式编排：

```python
chain = RunnablePassthrough.assign(...) | prompt | model | output_parser
```

这种写法的好处：
- 代码清晰，一眼看懂数据流
- 自动并行（RunnablePassthrough.assign）
- 天然支持流式输出
- 可组合、可测试

### 4.2 @tool 装饰器的本质

`@tool` 不只是"注册工具"，它做了三件事：
1. 从函数签名和 docstring 生成 Tool Schema
2. 把函数包装成 BaseTool 对象
3. 让 LLM 能"看到"并调用这个工具

理解了这一点，就理解了 Agent 工具调用的本质。

### 4.3 contextvars 在 Agent 中的妙用

工具函数被 LangGraph 调用时，没法直接传参进去。用 `contextvars` 实现线程级全局变量，是 Agent 开发中非常实用的模式。

```python
# 设置
token = set_case_context(context)
try:
    agent.invoke(...)
finally:
    reset_case_context(token)

# 使用
context = get_case_context()
```

## 五、工程实践收获

### 5.1 AI Vibe Coding 的效率

借助 AI 编程工具（Trae / Claude），开发效率大幅提升：
- 项目骨架生成
- 单元测试编写
- 重构辅助
- Bug 定位

但 AI 只是"副驾驶"，架构设计和关键决策还是要人来把控。

### 5.2 测试驱动开发（TTD）的价值

为每个模块写单元测试，好处是：
- 重构时不怕改坏（有测试兜底）
- 理解代码最快的方式是读测试
- Bug 修复后回归测试

### 5.3 分层架构的重要性

```
入口层 → Agent层 → 业务层 → 基础设施层
```

各层之间职责清晰，便于：
- 单独测试
- 替换组件（比如换个 LLM 供应商）
- 新人理解项目
