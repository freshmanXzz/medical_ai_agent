## Agent 架构演进路线

> 当前 Martin 是 **单 Agent + ReAct + Routing** 模式（LangGraph `create_agent` + 6 个工具 + DeepSeek Function Calling）。按照 Anthropic Building Effective Agents 框架，未来从"LLM 选路"逐步升级到"LLM 自主行动"再到"多 Agent 协作"。

### 📍 当前阶段：单 Agent + ReAct + Routing（v0.4）

```
用户输入 → LLM 判断意图 → Routing 选择工具 → 执行 → Observation → LLM 判断下一步 → ... → 最终回答
                              │
                  ┌───────────┼───────────┐
                  ▼           ▼           ▼
            analyze_image  search_...  generate_report  ...（6 个工具）
```

- **LLM 角色**：决定走哪条路（Routing）、走几步（ReAct 循环）
- **代码角色**：提供工具（能做什么）、Prompt（怎么想）、循环框架
- **自主性**：中等（LLM 自主决定行动步骤，但工具是固定的）

### 🟡 中期：引入 Evaluator-Optimizer 模式（3-6 个月）

> 在报告生成环节，不是一个 LLM 一次产出就完了。再加一个"评估者"LLM 打分 —— 不合格就打回重写，循环直到达标。

```
检测结果 + 病例上下文
        │
        ▼
  生成器 LLM → 产出报告草稿
        │
        ▼
  评估者 LLM → 评分（准确性 / 完整性 / 可读性）
        │
   ┌────┴────┐
   │ 达标？   │
   ├─ 是 ──→ 输出最终报告
   └─ 否 ──→ 带上修改意见，回到生成器
```

- **LLM 角色**：生成（Worker）+ 评估（Evaluator）
- **代码角色**：协调循环（最多重写 N 次）、评分标准（rubric）
- **自主性**：较高（LLM 自主判断质量是否达标）
- **对应里程碑**：多 Agent 协作 → 检测 Agent + 诊断 Agent + 报告 Agent + 协调 Agent

### 🔴 长期：Orchestrator-Worker 模式（6-12 个月）

> 一个"总协调 Agent"把复杂病例分析拆解成子任务，分派给 4 个专业 Agent，再汇总结果。

```
医生说："综合分析这个患者的所有资料"
        │
        ▼
┌──────────────────────┐
│   协调 Agent          │
│   拆解任务 + 分配      │
└──┬───────┬───────┬───┘
   │       │       │
   ▼       ▼       ▼       ▼
┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
│检测   │ │诊断   │ │报告   │ │知识   │
│Agent  │ │Agent  │ │Agent  │ │Agent  │
│影像   │ │推理   │ │撰写   │ │检索   │
│分析   │ │诊断   │ │排版   │ │指南   │
└──┬───┘ └──┬───┘ └──┬───┘ └──┬───┘
   │       │       │       │
   └───────┴───────┴───────┘
           │
           ▼
     协调 Agent 汇总
           │
           ▼
     最终综合分析报告
```

- **LLM 角色**：协调（Orchestrator）4 个 Worker Agent 各自独立决策
- **代码角色**：Agent 间通信协议、结果合并逻辑
- **自主性**：最高（多个 LLM 协作完成复杂任务）
- **对应里程碑**：多 Agent 协作 → 检测 Agent + 诊断 Agent + 报告 Agent + 协调 Agent

### 架构演进一览

| 阶段 | 时间 | 模式 | LLM 角色 | 自主性 | 关键变化 |
|------|------|------|----------|--------|----------|
| 📍 当前 | v0.4 | 单 Agent + ReAct + Routing | 决策者 | 中 | 1 个 Agent 管全部 6 个工具 |
| 🟡 中期 | v0.6 | + Evaluator-Optimizer | 生成者 + 评估者 | 较高 | 报告生成加入"评估→重写"循环 |
| 🔴 长期 | v0.8+ | Orchestrator-Worker | 协调者 + 4 Worker | 最高 | 1 个总控 + 4 个专业 Agent 并行 |

## 短期规划（1-3个月）

### 🎯 网页端 CT 影像展示与阅片（医生 Copilot 核心能力）

> **定位**：面向临床医生的 AI 影像 Copilot，医生必须能直接查看原始 CT。当前工作站中栏仅展示 AI 的结构化分析画布，不是实际影像阅片器；本项将把它升级为真实的网页端影像展示能力。

- [ ] **CT 图像浏览器** — 在 Web 端渲染 NIfTI / DICOM 图像
  - 二维切片浏览：横断面 / 冠状面 / 矢状面三平面联动
  - 窗宽窗位调节（WW/WL）：肺窗、纵隔窗、骨窗等预设
  - 缩放、平移、切片滚动
  - 从 MinIO 流式加载 .nii.gz 文件
  - 技术选型：Cornerstone.js（DICOM 原生支持）或 VTK.js（3D 渲染）
- [ ] **结节标注叠加** — 将检测结果叠加到 CT 图像上
  - 在切片上用矩形框/圆形标注检测到的结节位置
  - 点击标注跳转到对应切片
  - 标注旁显示结节直径、置信度
- [ ] **影像浏览器集成到当前工作站** — 将真实阅片器嵌入 `CaseWorkspace` 中间“影像分析区”
  - 左栏继续负责上传与结节清单；中栏负责切片与标注展示；右栏保持诊断信息链
  - Martin Copilot 可引用当前切片位置，例如“请复核第 120 层的结节”
  - 支持 Agent 在回复与报告中引用切片编号和结节标注
