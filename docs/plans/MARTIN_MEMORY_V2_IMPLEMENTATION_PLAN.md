## 1. 基线与范围

- SqliteStore V1 于 2026-09-30 定验 `ACCEPTED`；V1.1 报告 Finding 回填和 2026-10-02 的九类记忆、Exact/Temporal/Semantic、Router、Selective Writer 已进入 `main`。历史证据见 `docs/refactor/SQLITESTORE_V1_LIVE_ACCEPTANCE.md`、`docs/plans/REFACTOR_PROGRESS.md`、`MEMORY_ARCHITECTURE_IMPLEMENTATION_REPORT.md`。
- `app.sqlite` 的确认事实与授权仍是权威来源；`memory.sqlite` 保存长期记忆及 Finding 投影；`sessions.sqlite` 保存 Thread checkpoint；独立向量库是可重建的语义投影，医学知识 Chroma 不存患者记忆。
- V2.1 先解决“来源、事实等级、有效状态、纠正与冲突、当前回答能否使用”。V2.2 处理增长和摘要，V2.3 测量质量、延迟及并发。现阶段不重复建设三种检索器、不迁移 PostgreSQL、不把确认医疗事实移入 Store。
- 本计划不包含真实 CT/MONAI 全链路、知识库临床内容验收或全面医疗安全认证。它们仍按各自项目门禁独立验证。

## 2. V2.1 数据与权威契约

1. **权威顺序**：确认的业务事实约束临床事实；当前医生明确要求优先于已保存的展示偏好；有效的历史记忆只提供有来源的上下文；模型推断不得自我晋升为确认事实。当前要求也不能改写确认测量值。
2. **新写入的来源**：使用现有 doctor/patient/case/thread ID。Agent 工具写入绑定真实 `HumanMessage.id`、选中原文及医生身份；显式 API 写入标为 `api_submission`，保存认证医生与提交 ID，`source_message_id` 为空；业务投影指向业务行。禁止生成不存在的消息引用。
3. **旧记录兼容**：读适配器保留已知坐标和时间，将缺失的消息级来源标为 `legacy_unknown`；不得补造消息 ID。旧版 `report_style` key/value 继续作为 V1 兼容投影，但新修订有独立 ID 和版本链；两者更新在同一个 Store batch 内完成。旧版 private/case 条目先带“来源未完整记录”标签，不自动升级为确认事实。
4. **状态与历史**：typed 记录以 `active/superseded/retracted/invalid` 表达可用性；撤回和改写记录 `actor_id/occurred_at/reason/target_id`，保留受权历史。普通列表和模型输入只见当前可用条目；审计入口可查看修订链。每次状态写入与当前值投影的同库一致性必须有真实 SQLite 测试。
5. **未核实声明**：新增受约束的 `clinical_claim`（或等价明确类型），只能表示医生陈述/待核实信息，附来源、目标坐标和 `verification_status=unverified`。其中的“过敏”等项目在业务库没有对应确认字段时，仅验收“不会当成确认事实”；业务确认入口另行设计。针对 Finding 的纠正只保存待处理声明，不直接修改 Finding。
6. **时间语义**：`observed_at` 是历史观察时间，不等于当前有效性；临时任务可设置时效。confirmed Finding 不因统一 TTL 被删除。旧观察保留于业务库，只能在当前问题中作为有日期的历史证据引用。

## 3. V2.1 分批交付

### Batch 0 — 固定基线和兼容契约

- 记录当前三个数据库、namespace、API、Prompt 注入和 V1/V1.1 验收口径；用隔离合成库复跑最小记忆、授权、REST/WS、报告测试。记录失败属于环境、既有问题还是本批变更。
- 确定 `SqliteStore.batch` 对覆盖/删除的实际语义、旧版偏好键与 typed 记录一致性、已有数据的读取形状；以测试探针作决定，不假设文档伪代码与已安装版本一致。
- 产物：基线记录与契约测试清单。门禁：V1 A/B/C 的可重复离线行为、跨医生/患者隔离及当前报告偏好不退化。

### Batch 1 — 来源与偏好修订

- 扩展 typed 元数据及读适配器，明确 `message`、`api_submission`、`business_event`、`legacy_unknown` 四种来源质量。API 直接写入不再把生成的提交 ID 作为消息来源；Agent 写入校验本轮真实消息 ID 和原文片段。
- 报告偏好改成独立修订记录与当前值投影。工具和 HTTP 路径都写入真实可得的来源信息；历史版本可受权查询。沿用 V1 `report_style` 返回形状，并验证旧数据跨进程重开仍可读。
- 同步检查当轮明确格式要求的覆盖规则。支持“这次不限字数”与保存的长期条件规则分别建模；不能把一次性要求误存为永久偏好。
- 门禁：来源完整的新写入可追踪；旧记录显式显示来源未知；偏好修订/重启后只应用当前有效版本；V1 报告格式校验不退化。

### Batch 2 — 纠正、撤回与声明

- 为明确的目标记忆增加改写/撤回操作及最小审计事件。以目标 `memory_id` 和当前授权定位对象；不允许凭模型猜测目标。修订链和当前投影同批落库，重复请求有幂等语义。保留原始记录供审计，普通检索不返回旧版或撤回版。
- 增加 `clinical_claim` 和结构化 `correction`：对 Finding 的纠正包含 `target_finding_id`、白名单字段、提议值与来源。无法解析目标的自由文本只能作为未核实陈述，不产生确定性字段冲突。
- 对已确认业务行做只读冲突校验，返回“当前确认值、医生提出的值、各自来源、处理状态”；真正修改业务事实仍走既有授权业务服务与审计链，不由记忆写入自动完成。
- 增加受权的历史查询及撤回/纠正 API；医生可看到来源和当前状态。Web 的最小记忆管理入口在 API 契约稳定后接入，不把原始对话全文放进列表或日志。
- 门禁：撤回后当前请求和新 Thread 都不再应用；旧版可审计；未核实过敏声明不成为业务事实；纠正与业务事实冲突被明确标出；写入失败不返回成功。

### Batch 3 — 全路径注入门禁与回归验收

- 在现有 `MemoryService`/Router 增加共同的注入资格判断：重新授权 → 坐标/来源核验 → 状态与时效 → 修订关系 → 业务冲突 → 排序与预算。应用于 typed Exact、Semantic 回源后的命中，以及旧版 snapshot 各分区；当前确认业务事实继续由 SQL 提供。
- 语义索引继续作为可重建投影。沿用现有 hit 后按 `memory_id` 回源校验，补撤回、失效、来源被删除和授权变更的测试。索引残留不能使旧记录重新进入 Prompt。
- 在 Prompt 中保留事实、未核实声明、历史讨论和冲突的来源标签；最终回答须呈现冲突或检索不可用，不能因记忆存在而把讨论说成确认诊断。当前医生当轮明确要求优先于旧偏好。
- 门禁：下面第 5 节的 A–L 场景及真实模型验收通过，再标记 V2.1 完成。

## 4. 迁移、失败和回退

- V2.1 采用增量字段/读适配器及版本化新写入；不批量重写未知患者数据。先在合成旧库验证重启、重复迁移、旧 `report_style` 兼容、部分来源缺失及中断恢复。运行数据的备份与迁移在实际实施时单独记录，数据库、备份和验收原文不入 Git。
- Store 故障时当前业务事实仍可分析，历史记忆依赖的结论必须标明不可用；仅向量故障时 Exact/Temporal 继续。源写失败不得声称“已保存”；索引写失败须明确“源已保存、索引暂不可用”。
- V2.1 不把进程内 `RLock` 解释为跨进程并发保障。多 worker 写冲突与锁等待在 V2.3 测量；若部署要求提前增加 worker，先完成并发门禁。
- 若批次失败，保留旧版读取路径和数据，暂停下一批并记录具体失败。回退代码不能丢失已写入的新版本/撤回历史；恢复旧版服务前须验证其不会重新应用已撤回的偏好。

## 5. 验证和完成定义

| 场景 | 最小检查 |
| --- | --- |
| A–C 偏好 | 跨 Thread 来源可查；当轮要求覆盖旧规则；新规则取代旧规则且历史可查 |
| D 撤回 | 撤回后 REST、WS、Agent Prompt 均不应用，受权审计仍可查看 |
| E–G 事实边界 | 未核实声明不写业务事实；Finding 纠正显出冲突但不自动改库；助手推断不能成为医生证据 |
| H 向量残留 | 旧向量命中被源记录状态/授权门禁拒绝 |
| I–J 隔离 | 同患者不同医生的私人记忆、不同患者记忆均零串档，撤销授权立即生效 |
| K 故障 | Store/向量分别注入故障；当前事实继续可用，缺失历史不编造，保存失败可检测 |
| L 时间 | 2024 的观察保留为历史，2026 值可为当前；无稳定病灶身份时不声称同一病灶增长 |

测试顺序：先为每个批次运行纯逻辑测试与真实 SQLite 重启测试，再运行 `tests/memory`、`tests/access`、Agent/API/REST/WS/报告相关测试；最后按实际环境运行可执行的全套回归。V1/V1.1 的偏好、6→8mm 比较、Store 故障降级必须保留。真实模型验收使用隔离合成数据，同时检查结构化检索证据和**最终公开回答**；覆盖偏好覆盖/撤回、声明与确认事实、Finding 冲突、旧向量、Store 故障、跨医生/跨患者隔离。未运行的真实 CT、知识语料或跳过测试不得写成通过。

V2.1 完成标准：新写入的来源可追踪或明确标为提交/未知；当前可用状态可解释；撤回与旧版不进入正常 Prompt；未核实声明不晋升为确认事实；确定性冲突被呈现；授权零串档；V1/V1.1 回归与隔离合成数据真实模型验收通过。提交验收报告时列出测试命令、结果、失败/跳过、最终回答语义复核和剩余限制。

## 6. 后续阶段边界

- **V2.2 记忆增长**：在 V2.1 生命周期稳定后，扩展现有 Writer 的重复/近重复判断；摘要只作为带来源指针的投影，源撤回则摘要失效或重建；建立可测的全局 Prompt token 预算、类型配额和省略原因。原始业务 Finding 不因摘要或 TTL 被删。
- **V2.3 运行可靠性**：建立召回相关性、无关注入、来源覆盖、冲突发现、错误作用域/失效条目泄漏、延迟、超时及 SQLite 多进程争用指标。权限/失效泄漏在合成确定性场景必须为零；性能阈值先测基线再定。只有可复现的锁争用、延迟或部署拓扑证据才提出 PostgreSQL 独立迁移计划。
- **并行业务任务**：稳定跨检查病灶 ID 属于业务实体和影像核验链。V2.1 先保证“已确认同一病灶”“仅弱匹配观察值”“无法确认连续性”三种表达不混淆；真实 ID 建模、历史回填和人工确认另出业务设计及验收。
