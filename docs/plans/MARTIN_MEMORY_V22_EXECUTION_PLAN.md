## 1. V2.2 的目标与非目标

V2.1 解决「记忆是否可信、可追源、可撤回」。

V2.2 解决：**当长期记忆数量和会话跨度增加时，如何避免重复、摘要失真、检索上下文拥挤、关键证据被静默裁剪**。

V2.2 的核心交付：

- 在现有 Selective Writer 上实现**风险分级去重**；
- 建立**有来源的长期记忆滚动摘要**，并可靠处理源记录生命周期；
- 建立**任务感知的全局 Prompt 预算管理**、关键内容保护、可解释的省略记录；
- 在关键证据超预算时**有界分阶段处理**并在无法保证完整性时明确降级；
- 提供**授权管理员可调的预算管理界面**，但安全硬上限由后端实施；
- 完成 P0 硬约束、P1 质量对照、真实模型与 REST/WS/前端完整链路验收。

本轮**不做** PostgreSQL 迁移、完整 Stable Lesion ID 建模、真实 CT 推理临床验收、多进程争用专项优化、替换 BGE 或重造检索通道。V2.3 的完整可靠性指标体系留到后续，V2.2 只测足以证明当前改动安全有效的基线。

## 2. 八项已经确认的产品/架构决策（不可擅自重新选择）

| # | 主题 | 已确认结论 |

## 3. 存储、权限和临床权威边界（贯穿全阶段）

1. **Business DB**：已确认 Finding、检查、报告与业务授权的事实真相来源。历史检查记录不得因摘要、去重、TTL 或 Prompt 限制被物理删除、覆盖或缩成不可逆摘要。
2. **Long-term Memory**：医生偏好、医生既往决策理由、讨论上下文、任务、纠正及待核实声明等跨会话资料；它们不是天然确认的医疗事实。
3. **Checkpoint / 当前会话**：用于恢复线程状态，与跨会话长期记忆治理不同；不要混淆会话消息压缩与长期记忆 consolidation。
4. **知识 RAG**：医学文献/指南检索与患者/医生私有记忆分区、分权，不能交叉污染。
5. **历史有效 ≠ 当前有效**：例如 2024 年 6mm 仍为历史观察，但不能冒充当前大小。不能依赖“90 天后销毁检查”规避时效问题。
6. **病灶连续性**：已确认同一病灶、仅弱匹配、无法确认关联，三种表达必须有区别；V2.2 不建立新的稳定病灶 ID 系统。
7. **医生与患者隔离**：医生级通用偏好可跨其授权患者使用；医生私有患者讨论不得因共享病例权限而自动跨医生共享；患者 Alpha 不得串到 Beta。
8. **未核实声明**：例如口述过敏史可以按已通过 V2.1 的规则作为待核实声明存在，不能因为重要性高、摘要出现或重复多次就变成已确认事实。
9. **Assistant 推断**：模型自己的推测不得经多轮摘要/合并/检索形成自我强化的临床“事实”。

## 4. 工作流 A：风险分级去重（D2）

### 4.1 复用现有 Writer

在已有 Selective Writer、V2.1 revision/retraction 和来源链上扩展，不另造第二套互相冲突的写入系统。

概念上区分：

```text
new candidate
  ├─ same scope + truly equivalent       → duplicate / reinforce provenance
  ├─ preference refinement / revision    → V2.1 revision/supersession
  ├─ clinically distinct                 → independent memory
  ├─ ambiguous high-risk clinical overlap→ keep separate / review candidate
  └─ unrelated                           → new memory
```

### 4.2 自动化边界

- 仅在主体、医生/患者/病例 scope、记忆类型、逻辑命题及时间语义一致时，才考虑自动去重。
- 低风险偏好/工作流习惯可以自动合并**真正等价**表达，但保留有意义的原始来源及版本关系。
- 「普通报告 ≤ 200 字」和「复杂病例可详细写」属于条件细化，**不得**只按相似度做 duplicate。
- 不同检查、不同观察时点、不同病灶、不同证据理由，即使高度相似也不得自动合并成一条“确认事实”。
- 对临床决策、未核实病史、敏感声明，默认保留独立记录；有足够结构化依据时可标记待审核，不强制实现复杂审核队列，除非现有 UI 易于复用且确有需求。
- 任何合并/抑制写入/修订需能解释理由；不得丢 provenance 或使被撤回源恢复有效。

具体 similarity 算法及阈值由 Codex 基于现有 embedding、测试样本和误合并案例选择；禁止直接照搬原 HTML 的 0.85 / 0.92 为语义等价真理。

## 5. 工作流 B：有来源的长期摘要（D1、D3）

### 5.1 摘要对象和意义

重点覆盖长期医生/患者讨论、历史决策理由、多次讨论形成的有效上下文；不要求把每类记忆都摘要。少量结构化偏好直接精确读取通常更合适。

```text
Source memory records (with provenance, scope, lifecycle)
                ↓ eligible / authorized / active source set
Derived rolling summary (projection; source pointers + version)
                ↓ eligibility / source status validation
Detailed summary available for on-demand injection
```

摘要**不是新事实的独立来源**。源记录依然存在且可审计；临床精确数值以 Business DB 为准。

### 5.2 混合触发

- 当同一合规 scope 的有效记忆增长达到**可配置规模或 Token 阈值**时触发异步归纳；
- 定期低优先级扫描作为补充，不把每轮主聊天变成必然耗时的摘要作业；
- 用现有可用的后台任务/调度设施；若项目缺少可靠 worker，先提供可安全执行、幂等的治理入口及测试，不能假设部署中天然有稳定后台进程；
- 幂等、防并发覆盖、增量状态/版本校验按项目实际选择最小安全设计。

### 5.3 源撤回后的即时阻断

P0 不变量：**任何已撤回、失效、被替代且不再适用的源，不得通过旧摘要重新进入当前回答。**

- 来源发生生命周期变更后，旧摘要在所有正常 retrieval/注入路径上**立即不可用**（可在写路径标 stale，或读路径进行强一致校验，具体由 Codex 定）。
- 异步重建可稍后完成，但不允许“旧摘要继续用着等后台修好”。
- 重建前可退回对授权、有效的原始记忆检索；如拿不到可靠背景，明确降级。
- 失败恢复、重复事件、summary source graph、scope 跨界与并发写都必须有测试。

### 5.4 两级注入

- **Level 0 极简患者背景**：每轮只构造必要、授权、可验证、明确标注时间与状态的简短背景；当前无患者则不注入患者背景。不得默认把全部待核实声明塞进去。
- **Level 1 详细长期摘要**：当当前问题、任务类型与长期上下文相关，且授权、有效、在预算内时才注入；允许与原始高价值记忆共存，但需去掉重复叙述。
- 不能将“摘要每轮必注入”作为固定逻辑；极简背景和滚动摘要是两个不同产物。

## 6. 工作流 C：全局上下文预算（D4、D6）

### 6.1 准确计数与统一上限

预算应由真实模型/Tokenizer/当前调用实际消息格式确定，而非中文字数推算。计入 system/developer 指令、对话、工具消息、检索结果、结构化封装和必要调用开销，并预留模型输出及估算误差。

概念上：

```text
usable_input_limit
  = verified_model_context_window
  - reserved_generation
  - safety_margin
```

实际应用时要避免把模型参数、工具 schema 开销、模型提供方计费口径混为一谈。出现计数不确定时取保守估算；不可因计数器缺失而关闭硬上限。

### 6.2 受保护内容与弹性部分

**受保护、不可静默丢弃**：当前用户/医生的核心问题与明确指令；完成当前医疗判断所必需的确认业务事实及其时间/来源；存在的重要 claim-vs-fact 或 correction-vs-business 冲突两侧；必要安全与权限约束。

这里的“受保护”不表示全部业务库内容都必须放进同一 Prompt。应当挑出当前任务**必要且有依据**的证据；如果无法纳入，转分阶段处理或明确降级，而不是悄悄裁掉。

**弹性竞争池**：医学 RAG 片段、长期语义记忆、历史决策详情、详细摘要、非必要的会话历史等。类别配额为**软配额**，可借用空闲部分；总上限由后端硬性执行。权限/失效过滤必须在预算分配前完成。

### 6.3 按任务动态分配

复用现有 Router/任务信号，按任务类别（举例：简单问答、报告生成、纵向随访）分配不同软配额，不必新建第二套不透明的 LLM Router。

- 问答：以当前具体证据为主，避免无谓加载全部 RAG/历史；
- 报告：当前 Finding + 必要临床背景 + 医生偏好优先，指南按需；
- 纵向/决策说明：时间观察、历史决策与证据来源占更大份额；
- 未识别任务：回退安全默认配置。

Codex 决定具体分类和比例，但不得超过同一套安全硬上限。预算软配额和参数应有可测配置版本。

### 6.4 可解释的裁剪/过滤 trace

逐项记录选择/省略的**阶段与原因**，例如：

- 资格过滤：`scope_denied`、`inactive`、`superseded`、`source_retracted`、`summary_stale`；
- 质量过滤：`duplicate`、`irrelevant`、`low_priority`；
- 预算裁剪：`budget_exceeded`、`category_quota_pressure`、`covered_by_summary`；
- 系统降级：`store_unavailable`、`semantic_unavailable`、`tokenizer_unavailable`（按真实情况）。

原因命名由 Codex 决定；不能把“无权限/已撤回”记录成仅仅“预算不够”。

Trace 需要有请求 ID、策略版本、类别、条目引用、估算/实际 Token、入选状态和原因。**避免将完整 PHI/患者私密对话复制到普通日志。**

## 7. 工作流 D：关键证据超预算的分阶段处理（D5）

只有在完成低价值裁剪、去重、必要证据识别后，仍无法可靠容纳关键内容时才触发；不是每次问题都做额外多轮总结。

```text
Necessary evidence exceeds single-pass budget
                ↓
Split along safe domain boundaries (study/date/source/type)
                ↓
Pass-level structured extraction + source pointers
                ↓
Merge checked intermediate evidence
                ↓
Final answer with provenance and limits
                ↓
If completeness cannot be guaranteed → explicit degradation
```

设计约束：

- 每批处理仍遵守权限、生命周期、Token 上限；
- 原始已确认临床事实不因中间模型归纳被覆盖；
- 中间结论保留来源、时间、状态，不能把推测升级为事实；
- 显式限制批次数、总 Token/时延/成本或采用已有系统预算上限，防止失控循环；
- 完整性检查至少能识别未处理批次、冲突遗漏、来源失效、病例关联不明；
- 无法完整覆盖时，最终回答应清楚说明“已处理范围/遗漏范围/不能作出的判断”；
- 实现上可复用现有流水线/子步骤，不强制引入复杂工作流框架。

**注意**：此处是同一次请求内的多步骤处理逻辑设计，不意味着应用可以无保障地承诺异步答复或在后台替用户完成临床分析。

## 8. 工作流 E：预算配置与管理员 UI（D7）

- 后端定义和强制执行**不可越过的安全硬上限**及安全默认值；
- 管理员 UI 在允许范围内调整任务级软配额、摘要/极简背景预算及合理触发参数；
- 普通医生角色只可使用，不得通过 UI、REST、WS 或伪造角色参数改写系统预算；
- 参数变更经过权限校验、范围与总量校验；保留变更人、时间、前后值、策略版本；提供回退；
- 并发冲突、非法配置、缺失配置、旧版本配置采用安全回退策略；
- UI 展示真实后端生效版本、预算使用与省略原因，而不是只渲染无法落地的本地滑块；
- 依当前 V2.1 memory management UI / 项目权限模型最小扩展，不独立搭一套管理员体系。

对于 UI 是否需要额外筛选、预览、保存确认、版本列表，由 Codex 判断现有系统交互模式后实现合理的最小方案。

## 9. 与原 HTML 方案的采用和修订边界

| 原方案参考 | V2.2 处理决定 |
|---|---|
| 三通道写入、统一入口、审核与审计 | **参考思想**，复用已完成的 Selective Writer/V2.1，而不是重写三通道。 |
| 语义相似度阈值 0.85、0.92 自动合并 | **不照搬固定值**；分级自动化 + 结构化同一性约束 + 样本验证。 |
| 覆盖/软删除旧记忆 | 保留 V2.1 revision/retraction/provenance 语义，不物理清掉原始证据。 |
| 每周整理、条目 >50 时触发 | 作为候选策略；具体频次/阈值由基线数据与后台设施决定。 |
| 患者 `summary/rolling` | 参考派生摘要的思想；不是强制 namespace 或唯一记录结构。 |
| 每轮强制注入 rolling summary | **改为 D1：每轮极简背景 + 详细摘要按需注入**。 |
| 第 6 次检查压缩旧 findings，活跃 findings 只留 3 次 | **不能删/损害 Business DB 完整历史**；可在 Prompt 层摘要历史，但业务观察完整可查。 |
| 检查值默认 90 天 TTL | **不得直接删除历史观察**；必须区别历史有效与当前有效。 |
| 记忆 400 / RAG 1500 / 历史 2000 固定分区 | **改为 D4+D6**：有硬上限、软配额和任务动态分配。 |
| 相关性 × 时间 × 重要性，医学重要记忆优先 | 可以参考，但必须先验来源权威与权限；高风险未核实声明不能因“重要”就变确认事实或跨作用域必注入。 |
| 组件 TS + E2E TC 三层证据 | 保留并扩展：存储/治理、注入 trace、模型最终回答层。 |
| Store 故障时主流程降级 | 保留 V1/V2.1 的安全降级；不得虚构历史。 |
| Postgres 作为默认下一阶段 | **不直接执行**；留 V2.3 压测及证据驱动独立迁移计划。 |

**特别提醒**：原 HTML 是设计参考，可能包含与当前系统已完成实现不一致的类型、Embedding 维度、工具 API 或数据库假设；代码现状与最近验收报告优先。

## 10. P0 / P1 验收（D8）

### 10.1 P0：确定性硬约束，零容忍

以下应由隔离合成样本验证，**相关测试全部通过**。若有任何已发现违规，V2.2 不得宣称验收通过：

1. **授权隔离**：错误医生/患者/病例的私有记忆、摘要、trace 内容不泄漏；未授权管理员配置 API 不能改预算。
2. **生命周期**：失效、撤回、已替代且不适用的来源不可经摘要、向量命中或缓存复活；撤回与读取竞态必须有安全保障。
3. **临床事实边界**：未核实声明、Assistant 推测、历史观察不会被摘要/去重提升为确认业务事实或当前值。
4. **去重安全**：不同病灶、日期、决策依据的临床记忆不可仅凭近似表达自动合并；偏好 refinement 不被吞掉。
5. **摘要可追溯**：用于回答的摘要可以定位有效源；源撤回立即阻断旧摘要。
6. **预算硬上限**：测试中的最终上下文 Token 包络不能越界；关键必要信息不能静默丢弃，无法装入时有明确降级。
7. **关键冲突**：已识别的事实/纠正冲突，两侧有效证据不因裁剪而被悄悄抹去。
8. **原始历史**：治理任务不物理删除/不可逆覆盖完整 Business Finding；时效与随访查询仍可工作。
9. **配置安全**：管理员权限、配置合法性、版本审计、回退路径均有效；非法配置不得突破硬上限。
10. **存量回归**：V2.1 provenance、revision/retraction、claim/fact、Finding conflict、管理界面、REST/WS 行为不退化。

“零容忍”指对**构造的确定性验收场景必须零违规**，并非宣称通过有限测试就可以证明现实世界永远零风险。

### 10.2 P1：质量与资源效率（先基线再定阈值）

在 V2.1 或 V2.2 未启用相应新策略的可比基线上测量：

- 精确重复消除数与误合并率（低风险/临床高风险分类）；
- 近重复召回与保留新增信息的能力；
- 摘要压缩率、关键事实保留率、来源覆盖率、事实漂移/误归因；
- 生成与摘要作业 Token/模型调用成本；
- 任务类型维度的总 Prompt Token、有效信息密度、预算借用与省略原因覆盖；
- 最终回答的事实正确性、关键遗漏与来源准确性；
- 单次与分阶段调用的时延、失败率、降级比例。

由 Codex 提出**可复现样本、测量方法、基线结果、建议阈值和权衡**。尚无数据时先记录，不得编造 P1 门槛；临床关键错误不能被平均分数掩盖。

### 10.3 三层证据与真实模型验收

按以下层级收集结果：

- **存储/治理层**：写入与去重、Summary 版本与源链接、撤回传播、授权和审计；
- **注入/trace 层**：路由与预算选择、确切入选条目、遗漏理由、Token 合规、冲突保护；
- **生成层**：方舟真实模型在隔离合成患者/医生数据上的最终公开回答和报告，不只看检索是否命中。

跨会话验收需切换 thread/checkpoint，避免旧内容从短期上下文偷渡造成假阳性。可使用 LLM-as-judge 辅助评分，但关键医疗边界和隔离结果必须用确定性断言/人工复核补充。

## 11. V2.2 验收矩阵（至少涵盖）

| 场景 | 核心断言 |
|---|---|
| T01 完全相同偏好重复两次 | 不出现多条等价 active；来源追踪合理。 |
| T02 同义偏好反复表达 | 自动去重或强化同一偏好，避免 flood。 |
| T03 偏好条件细化 | 200 字普通报告 vs 复杂病例详写正确并存/修订，不被吞掉。 |
| T04 不同临床决策理由相似 | 不自动合并成一个理由。 |
| T05 相同位置不同时间/病灶 | 不因文字相似确认同一病灶。 |
| T06 长期讨论达规模阈值 | 摘要生成或进入可靠队列；源链、作用域正确；无原始记录删除。 |
| T07 来源撤回 + 并发读取 | 撤回后旧摘要不可被使用；未完成重建则用有效源或降级。 |
| T08 多轮滚动摘要 | 不自我强化推测；新旧源关系可复核。 |
| T09 每轮极简背景、详细摘要按需 | 简单问答不强塞长摘要；需要历史理由时可召回。 |
| T10 过期与历史观察 | 历史值仍在 Business DB，标明观察日期，不冒充当前值。 |
| T11 多通道预算竞争 | RAG/Exact/Temporal/Semantic/summary/会话统一计数，软配额可借用且不超硬限。 |
| T12 关键冲突超过预算 | 不静默裁掉一方；分阶段处理或明确降级。 |
| T13 大量无关近重复检索 | 有明确排重/省略理由，Prompt 不被 flood。 |
| T14 按任务动态配置 | 问答、报告、随访有效分配不同软配额，硬上限一致。 |
| T15 分阶段处理多年随访 | 各批次携来源，最终不丢关键时序；未覆盖内容明确提示。 |
| T16 源已撤回但 vector/cache 命中 | lifecycle filter 阻断污染。 |
| T17 Doctor A/B + Alpha/Beta | 记忆、摘要、诊断上下文、管理 trace 均不串档。 |
| T18 普通医生修改系统预算 | API 及 UI 均拒绝；权限不可由请求参数伪造。 |
| T19 管理员配置非法值/回退 | 服务器拒绝越界配置；合法变更有版本和审计，可回滚。 |
| T20 Store / embedding / summary job 故障 | 已确认业务事实仍按现有能力可用；缺失历史不编造；明确降级。 |
| T21 真实 REST / WS / 前端 | 用户看到的回答、报告与预算/摘要设置和 trace 的实际行为一致。 |
| T22 V2.1 全链路回归 | 老场景继续通过，记录所有失败/跳过/环境限制。 |

每项至少包含一个正例和一个反例/故障路径；测试语料必须用隔离合成数据。若新增 API，遵守现有认证和权限规范。

## 13. 与 Codex 的决策协作方式

**已经明确的八项方案不再反复征询。**以下为 Codex 自主权与需要提问的边界。

### Codex 可自行判断

- 类名、模块边界、数据 schema 与内部缓存结构；
- 复用或扩展现有 Writer/Router/UI/REST/WS 的具体方式；
- 去重候选召回策略、tokenizer 适配、summary 投影存储、摘要队列落点；
- 初始**测试参数**、可观察指标、合成样本和安全回退实现；
- 在保持八项决策前提下的最小兼容迁移。

### 遇到以下问题必须先询问用户

- 需要改变原始 Business Finding 的保留、授权或事实确认规则；
- 需要跨医生或跨患者共享新的患者私有记忆或摘要；
- 需要改变已确认的混合注入、分级去重、来源撤回即时阻断等八项决策；
- 需要破坏已验收行为、大规模迁移数据库或明显增加部署依赖；
- 测量结果显示某项设计无法在当前架构安全实现，需要业务上的取舍；
- 计划新增重大临床判断行为或扩大到真实 CT/Stable Lesion ID。

提问时一次聚焦一个设计主题，附：**当前实现 → 冲突或歧义 → 可行选项 → 推荐及依据 → 决策影响**。不要为普通代码组织细节反复打断。

## 15. V2.3 与并行业务事项继续保持原阶段边界

**V2.3 — Operational Reliability**：研究召回相关性、无关注入、provenance 覆盖、冲突发现、错误作用域/失效条目泄漏、延迟、超时、SQLite 多进程争用。权限或失效泄漏在合成确定性场景应为零；性能目标先测基线再定。只有可复现的锁争用、延迟或部署拓扑证据才提出 PostgreSQL 独立迁移方案。

**Parallel — Clinical Entity Continuity / Stable Lesion ID**：稳定跨检查病灶 ID、历史回填、人工确认属于 Business Entity/影像核验链；另出业务设计与验收，不混入 V2.2。

## 最终原则

> **不以更少 Token 交换更不可靠的医疗判断，不以更强的自动摘要换掉可追溯的原始事实。**
>
> V2.2 的目标是：**减少冗余、维持来源、保护关键证据、控制上下文成本，并在无法可靠完成时明确降级。**
